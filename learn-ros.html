How to follow this course

1

What ROS 2 is, and why robots use it

10 min
You will learn

what ROS 2 does for you, what it does not do, and how to install it and run your first two programs.

1.1 The problem ROS 2 solves

A robot runs many programs at the same time: one reads the camera, one reads the laser, one computes where the robot is, one plans the path, one drives the motors. They are written by different people, in different languages, and often run on different computers. They must talk to each other.

ROS 2 (Robot Operating System 2) is the free, open-source software that makes them talk. Despite its name it is not an operating system: it is installed on top of Linux (or Windows, macOS). It gives you three things:

WhatIn simple wordsExamples
The plumbingPrograms send each other messages without knowing where the other one runs.topics, services, actions
The toolsSee, record, replay and debug what happens inside the robot.ros2 commands, RViz, rosbag, Gazebo
The librariesReady-made, tested solutions to the hard problems.Nav2 (navigation), MoveIt 2 (arms), slam_toolbox (maps)
The key idea

With ROS 2 you do not write one big program. You write small programs that each do one job, and you connect them. You can then replace one of them (a real camera by a simulated one, your planner by a better one) without touching the others.

1.2 What ROS 2 is not

  • It is not a programming language: you write your nodes in Python or C++.
  • It does not replace the maths: the kinematics, the PID and the Kalman filter of the other courses are still there, inside the nodes.
  • It is not the safety system: an emergency stop never depends on ROS 2.

1.3 Versions (distributions)

ROS 2 is released once a year under a name. Some releases are supported for five years (LTS): choose one of these to learn. This course uses Jazzy Jalisco (2024, LTS, on Ubuntu 24.04); everything here also works on Humble (2022, LTS, Ubuntu 22.04) by replacing jazzy with humble. For a newer release, check docs.ros.org: the ideas of this course do not change.

ROS 1 is finished

The first ROS (ROS 1, last version “Noetic”) reached its end of life in 2025. Many old tutorials still use it: if you see roscore, rosrun or catkin_make, it is ROS 1. In ROS 2 the commands start with ros2 and the build tool is colcon.

1.4 Install it and say hello

The simplest way is a computer (or a virtual machine) with Ubuntu. The official guide on docs.ros.org gives the exact steps to add the ROS 2 package source; then:

# Ubuntu 24.04 + ROS 2 Jazzy (after adding the ROS 2 apt repository, see docs.ros.org)
sudo apt install ros-jazzy-desktop          # ROS 2, RViz, demos
sudo apt install python3-colcon-common-extensions

source /opt/ros/jazzy/setup.bash            # in every new terminal (or put it in ~/.bashrc)

ros2 run demo_nodes_cpp talker              # terminal 1: publishes "Hello World: 1, 2, 3..."
ros2 run demo_nodes_py listener             # terminal 2: prints what it hears

The talker and the listener are two separate programs. They found each other alone, with no address to configure: this is the plumbing of ROS 2 at work.

The most common beginner error

ros2: command not found means you forgot source /opt/ros/jazzy/setup.bash in this terminal. Every new terminal needs it.

  • LTS

  • A robot is split into small programs (nodes) that each do one job.

Nodes, topics and messages

12 min
You will learn

how nodes exchange data with topics, what a message is, and the commands to look inside a running robot.

2.1 Publish and subscribe

A node is one running program. A topic is a named channel, like a radio station. A node that has data publishes it on a topic; every node that wants this data subscribes to the topic. The publisher does not know who listens, and it does not wait for an answer.

  • One topic can have several publishers and several subscribers.
  • Topics are for data that flows all the time: sensor readings, positions, speed commands.
  • Names look like paths: /scan, /cmd_vel, /camera/image_raw.

2.2 Messages have a type

Every topic carries messages of one type, known in advance. A type is a list of named fields. The most used ones:

TypeContainsTypical topic
std_msgs/msg/Stringa text/chatter
geometry_msgs/msg/Twista speed command: linear.x (m/s, forward) and angular.z (rad/s, turning)/cmd_vel
sensor_msgs/msg/LaserScanone turn of a laser scanner: a list of distances ranges, the first angle and the angle step/scan
sensor_msgs/msg/Imagea camera image/camera/image_raw
nav_msgs/msg/Odometrythe position and speed of the robot, from its wheels/odom
sensor_msgs/msg/JointStatethe angle and speed of every joint of an arm/joint_states
Units: always the same

ROS uses SI units everywhere: metres, seconds, radians, kilograms. Never degrees, never millimetres. The x axis of a robot points forward, y to the left, z up.

2.3 Look inside a running robot

Keep the talker and the listener of lesson 1 running, open a third terminal, and try:

ros2 node list                    # which nodes are running?
ros2 topic list -t                # which topics exist, and their message type
ros2 topic echo /chatter          # print the messages of a topic
ros2 topic hz /chatter            # how many messages per second?
ros2 topic info /chatter -v       # who publishes, who subscribes, with which QoS
ros2 interface show geometry_msgs/msg/Twist    # what is inside a message type

# publish by hand: drive a robot forward at 0.2 m/s while turning at 0.5 rad/s, 10 times per second
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.2}, angular: {z: 0.5}}"

rqt_graph                         # draw the graph of nodes and topics

These few commands are how you debug 90 % of ROS 2 problems: is the node running, is the topic there, does data flow, at which rate, with the right type?

2.4 Quality of service (QoS), in short

Each publisher and subscriber chooses how messages are delivered. Two settings matter at the beginning:

SettingChoiceUse it for
Reliabilityreliable: lost messages are sent againcommands, states, maps
Reliabilitybest effort: a lost message is forgotten, the next one comes soonfast sensors: laser, camera, IMU
History depthhow many messages wait if the subscriber is slow (often 10)every topic
A topic with no data? Check the QoS

A reliable subscriber does not receive anything from a best effort publisher: the two are not compatible, and there is no error message. If ros2 topic echo shows data but your node receives nothing, compare the QoS with ros2 topic info -v.

  • node
  • topic
  • publisher
  • subscriber
  • message type
  • quality of service (QoS)
The essentials
  • A node publishes messages on a topic; any node can subscribe to it. Nobody answers.
  • Each topic has one message type. Units are always metres, seconds and radians.
  • ros2 topic list / echo / hz / info show what really happens.

3.1 Workspace and package

3.2 A publisher

File my_robot/my_robot/talker.py. Read it from top to bottom: a node is a class; it creates a publisher and a timer; the timer calls tick(), which publishes one message.

import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class Talker(Node):
    def __init__(self):
        super().__init__('talker')                               # the name of the node
        self.pub = self.create_publisher(String, 'chatter', 10)  # type, topic, queue size
        self.timer = self.create_timer(0.5, self.tick)           # call tick() every 0.5 s
        self.count = 0

    def tick(self):
        msg = String()
        msg.data = f'Hello robot: {self.count}'
        self.pub.publish(msg)
        self.get_logger().info(f'I said: "{msg.data}"')
        self.count += 1


def main():
    rclpy.init()
    node = Talker()
    try:
        rclpy.spin(node)             # wait and run the callbacks until Ctrl+C
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()

3.3 A subscriber

File my_robot/my_robot/listener.py. The subscriber gives ROS 2 a function, called a callback: ROS 2 calls it each time a message arrives.

import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class Listener(Node):
    def __init__(self):
        super().__init__('listener')
        # heard() is called each time a message arrives on the topic "chatter"
        self.sub = self.create_subscription(String, 'chatter', self.heard, 10)

    def heard(self, msg):
        self.get_logger().info(f'I heard: "{msg.data}"')


def main():
    rclpy.init()
    node = Listener()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()
How a node really works

rclpy.spin(node) is a loop that waits. When a timer fires or a message arrives, it runs the matching callback, then waits again. So a callback must be short: while it runs, the node does nothing else. Never put time.sleep(5) or a long while loop inside a callback.

3.4 The pattern of every robot node

  1. Subscribe to the sensors: each callback only stores the last value.
  2. A timer at a fixed rate (10 to 100 Hz) reads these values, computes, and publishes the command.
  3. This is the loop “sense, think, act” of the first course, written with ROS 2. You will use it in lesson 9.
Three classic mistakes
  • You changed the code but nothing changes: you forgot colcon build (or use --symlink-install once, so Python files are linked, not copied).
  • Package 'my_robot' not found: you forgot source install/setup.bash in this terminal.
  • No executable found: the node is missing in entry_points of setup.py.

Python (rclpy) is perfect to learn and for most nodes. C++ (rclcpp) has the same ideas and the same names; it is used when speed matters (drivers, control loops, image processing).

The essentials
  • A node is a class: it creates publishers, subscribers and timers.
  • ROS 2 calls your callbacks when a message arrives or a timer fires; keep them short.

Messages arrive at 10 Hz. Your callback takes 0.3 s. The queue holds 10 messages. After how many seconds is it full?

Each second 10 messages arrive and 1 / 0.3 are processed.

    It waits, and runs the callbacks of the node (timers, messages) each time one is due, until the program is stopped.

  2. Why must a callback be short?

    While one callback runs, the node cannot run the others: messages wait and timers are late.

  3. After colcon build, which command makes your package visible in a terminal?

    source install/setup.bash, from the workspace folder.

Services, actions and parameters

You will learn

the three other ways nodes communicate, and how to choose between a topic, a service and an action.

4.1 Four tools, four jobs

ToolLike…How it worksUse it for
Topica radio stationone way, all the time, nobody answerssensor data, speed commands
Servicea phone call with a quick questionone request, one answer, right away“switch the light on”, “save the map”, “compute this”
Actionordering a pizza: you follow the delivery and can cancela goal, then progress reports, then a result“go to the kitchen”, “move the arm along this path”
Parametera setting of the nodea named value, read at start or changed while runningmaximum speed, gains, name of a file
How to choose
  • Data that flows without being asked → topic.
  • A question with a quick answer (less than a second) → service.
  • A task that takes time, that you want to follow or cancel → action.

4.2 A service and a parameter in Python

This node offers the service add_two_ints: it receives two numbers and answers with their sum. It also has a parameter offset. (Add example_interfaces to the dependencies in package.xml, and the node to setup.py.)

import rclpy
from rclpy.node import Node
from example_interfaces.srv import AddTwoInts      # request: a, b   response: sum


class Adder(Node):
    def __init__(self):
        super().__init__('adder')
        self.srv = self.create_service(AddTwoInts, 'add_two_ints', self.add)
        self.declare_parameter('offset', 0)          # a parameter, with its default value

    def add(self, request, response):
        offset = self.get_parameter('offset').value
        response.sum = request.a + request.b + offset
        self.get_logger().info(f'{request.a} + {request.b} (+ {offset}) = {response.sum}')
        return response


def main():
    rclpy.init()
    node = Adder()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()

Call it from the terminal, then change the parameter while the node runs:

ros2 run my_robot adder                                   # terminal 1: the server

ros2 service list -t                                      # terminal 2
ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 2, b: 3}"
#   -> response: example_interfaces.srv.AddTwoInts_Response(sum=5)

ros2 param list /adder
ros2 param set /adder offset 10                           # change the parameter while the node runs
ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 2, b: 3}"
#   -> sum=15

ros2 action list -t                                       # the actions, if a node offers some

Launch files: start a whole robot with one command

10 min
You will learn

to start many nodes at once with their parameters, and to rename topics and group robots without changing the code.

5.1 Why launch files

A real robot runs 20 to 50 nodes. Nobody opens 50 terminals. A launch file is a list of the nodes to start, with their settings. One command starts everything, and Ctrl+C stops everything.

from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node


def generate_launch_description():
    return LaunchDescription([
        DeclareLaunchArgument('robot', default_value='r1'),   # ros2 launch ... robot:=r2

        Node(package='my_robot', executable='talker',
             namespace=LaunchConfiguration('robot'),           # topics become /r1/...
             remappings=[('chatter', 'news')],                 # (name in the code, name on the network)
             output='screen'),

        Node(package='my_robot', executable='listener',
             namespace=LaunchConfiguration('robot'),
             remappings=[('chatter', 'news')],
             output='screen'),

        Node(package='my_robot', executable='adder',
             parameters=[{'offset': 10}]),                     # or a YAML file
    ])
# the file is my_robot/launch/demo.launch.py; add to setup.py (data_files):
#   (os.path.join('share', package_name, 'launch'), glob('launch/*.launch.py')),
colcon build --symlink-install && source install/setup.bash

ros2 launch my_robot demo.launch.py                # starts the three nodes
ros2 launch my_robot demo.launch.py robot:=r2      # same nodes, for a second robot
ros2 launch my_robot demo.launch.py --show-args    # which arguments does it accept?

5.2 Three ways to adapt a node without touching its code

ToolWhat it changesExample
Parametersthe settings of the nodeparameters=[{'speed': 0.3}], or a YAML file
Remappingthe name of a topicthe node publishes scan, the robot expects front_laser/scan
Namespacea prefix on every name of the nodetwo robots: /r1/cmd_vel and /r2/cmd_vel
Why node code uses names without a slash

In lesson 3 the topic was 'chatter', not '/chatter'. A name without a leading slash is relative: it takes the namespace of the node. The same code then works for robot 1 and robot 2. A name that starts with / is absolute and ignores the namespace.

5.3 Parameters in a YAML file

When a node has many parameters, put them in a file config/params.yaml and give its path in parameters=[…]:

safe_driver:                 # the name of the node
  ros__parameters:
    speed: 0.15
    stop_distance: 0.40

Launch files can also include other launch files: this is how the big stacks start. One line includes the whole navigation system.

The layout of a tidy package
my_robot/
  package.xml          dependencies
  setup.py             nodes and installed files
  my_robot/            the Python nodes
  launch/              *.launch.py
  config/              *.yaml (parameters)
  urdf/                the model of the robot (lesson 6)

6

Frames and the robot model: tf2 and URDF

14 min
You will learn

how ROS 2 keeps track of every frame of the robot, and how to describe a robot in a URDF file.

6.1 The question tf2 answers

The camera sees a cup at 0.6 m in front of it. Where is the cup for the gripper? For the map? You know the answer from the modelling course: multiply the homogeneous matrices from one frame to the other. tf2 is the ROS 2 library that does it for you, for all the frames, all the time.

Every frame has a name and exactly one parent: the frames form a tree. Each link of the tree is a transform (a translation and a rotation) published on the topics /tf and /tf_static.

FrameWhat it is
base_linkthe body of the robot: x forward, y left, z up
odomwhere the robot started. odom → base_link comes from the wheels: smooth, but it drifts.
mapthe fixed frame of the map. map → odom comes from the localisation: it corrects the drift, with small jumps.
laser_link, camera_link…one frame per sensor, fixed on the body

6.2 URDF: the robot in a file

A URDF file describes the robot as links (rigid parts) joined by joints, exactly the chain of the first course. Each joint says: its parent link, its child link, where it is (origin), around which axis it moves, and its type (revolute, prismatic, continuous, fixed). Here is the 2-axis arm of the maths course:

<?xml version="1.0"?>
<robot name="two_axis_arm">
  <link name="base_link">
    <visual><geometry><cylinder radius="0.10" length="0.05"/></geometry></visual>
  </link>

  <link name="link1">
    <visual>
      <origin xyz="0.25 0 0"/>                       <!-- the box is centred in the middle of the link -->
      <geometry><box size="0.50 0.05 0.05"/></geometry>
    </visual>
  </link>

  <link name="link2">
    <visual>
      <origin xyz="0.20 0 0"/>
      <geometry><box size="0.40 0.04 0.04"/></geometry>
    </visual>
  </link>

  <joint name="joint1" type="revolute">              <!-- theta1 -->
    <parent link="base_link"/> <child link="link1"/>
    <origin xyz="0 0 0.05"/> <axis xyz="0 0 1"/>
    <limit lower="-3.14" upper="3.14" effort="10" velocity="2"/>
  </joint>

  <joint name="joint2" type="revolute">              <!-- theta2, at the end of link1 (L1 = 0.5 m) -->
    <parent link="link1"/> <child link="link2"/>
    <origin xyz="0.5 0 0"/> <axis xyz="0 0 1"/>
    <limit lower="-2.6" upper="2.6" effort="10" velocity="2"/>
  </joint>
</robot>

The node robot_state_publisher reads the URDF and the joint angles (topic /joint_states) and publishes all the frames of the robot on tf: it computes the forward kinematics for you.

#   -> RViz shows the arm, and a small window with one slider per joint

ros2 run tf2_ros tf2_echo base_link link2          # where is link2, seen from the base?
ros2 run tf2_tools view_frames                     # writes frames.pdf: the whole tree

# a fixed frame, for example a camera 0.2 m in front of the base and 0.5 m above it

Check the forward kinematics yourself

Set joint1 = 0.5 rad and joint2 = 0.8 rad with the sliders. The origin of link2 is at the end of link 1: x = 0.5 cos 0.5 = 0.439 m, y = 0.5 sin 0.5 = 0.240 m, z = 0.05 m. tf2_echo base_link link2 must print the same translation. It is the formula x = L₁ cos θ₁ of the maths course, computed by ROS 2.

6.3 RViz: see what the robot thinks

RViz is the 3D viewer of ROS 2. It does not simulate anything: it draws the data that the nodes publish (the robot model, the frames, the laser points, the map, the planned path). Choose the Fixed Frame at the top left (base_link, odom or map), then add displays.

Typical tf problems
  • “frame does not exist” or two separate trees: a link of the tree is missing. Look at the PDF of view_frames.
  • The sensor data appears at the wrong place: the origin of the sensor in the URDF is wrong (measure it on the real robot).
  • “extrapolation into the future”: the clocks of two computers differ, or simulated time is not enabled (use_sim_time).

7.3 The three topics of a mobile robot

TopicDirectionContent
/cmd_velyou → robotthe speed you ask: linear.x (m/s) and angular.z (rad/s). The robot converts it into wheel speeds (mobile robot course).
/odomrobot → youwhere the robot thinks it is, by counting wheel turns
/scanrobot → youthe distances measured by the laser, one per angle
Read a laser scan

A scan has angle_min = 0, angle_increment = 0.0175 rad (1°) and 360 values in ranges. The beam number i points at the angle angle_min + i × angle_increment: ranges[0] is straight ahead, ranges[90] is to the left, ranges[180] is behind. A value of inf means “nothing seen”.

7.4 Simulated time

A simulator can run slower or faster than a real clock. It publishes its own time on the topic /clock. Every node that works with a simulation must use it: set the parameter use_sim_time:=true. Forgetting it gives strange tf errors.

Why rosbag is precious

A bug that happens once an hour on the real robot is very hard to study. Record a bag during the tests: when the bug happens, you replay the exact same sensor data at your desk, as many times as you want, and you test your fix on it.

8.1 Nav2: from A to B

  • Localisation (AMCL) compares the laser with the map to find where the robot is: it publishes map → odom.

8.2 MoveIt 2: move an arm without collision

  1. It reads the URDF of the arm and a description of the obstacles.
  2. You give a target for the tool. MoveIt solves the inverse kinematics.
  3. It plans a path in the joint space that touches nothing (RRT and its cousins).
  4. It turns the path into a trajectory with speeds and accelerations inside the limits.
  5. It sends it to the arm with the action FollowJointTrajectory.

8.3 ros2_control: the last metre before the motors

ros2_control separates two things. A hardware interface talks to the real motors (or to the simulator): it reads positions and writes commands. Controllers are plugged on top: diff_drive_controller turns /cmd_vel into wheel speeds and computes the odometry; joint_trajectory_controller follows the trajectories of MoveIt. To change the robot you only change the hardware interface.

ROS 2 and safety

These stacks are powerful but they are not certified safety systems. A node can crash, a message can be late. The emergency stop, the safety laser scanner and the speed limits of a real robot stay in certified hardware, outside ROS 2 (see the lesson on safety in “Robots in the real world”).

Project: a robot that drives and avoids obstacles

You will learn

9.1 The plan

The robot drives straight ahead. When the laser sees an obstacle closer than 40 cm in front, the robot turns on the spot until the way is free. It is the loop sense → think → act:

9.2 The node

File my_robot/my_robot/safe_driver.py (declare it in setup.py, and add geometry_msgs and sensor_msgs to package.xml). It follows the pattern of lesson 3: the laser callback only stores the nearest distance in front; a 10 Hz timer decides and publishes.

import math

import rclpy
from rclpy.node import Node
from rclpy.qos import qos_profile_sensor_data
from geometry_msgs.msg import Twist
from sensor_msgs.msg import LaserScan


class SafeDriver(Node):
    """Drive forward, and turn on the spot when an obstacle is closer than stop_distance."""

    def __init__(self):
        super().__init__('safe_driver')
        self.declare_parameter('speed', 0.15)             # m/s
        self.declare_parameter('stop_distance', 0.40)     # m
        self.front = math.inf                             # nearest obstacle in front (m)
        self.cmd = self.create_publisher(Twist, 'cmd_vel', 10)
        self.scan = self.create_subscription(LaserScan, 'scan', self.on_scan, qos_profile_sensor_data)
        self.timer = self.create_timer(0.1, self.control)  # the control loop: 10 Hz

    def on_scan(self, msg):
        # keep the beams within 25 degrees of straight ahead (angle 0)
        near = []
        for i, r in enumerate(msg.ranges):
            angle = msg.angle_min + i * msg.angle_increment
            angle = math.atan2(math.sin(angle), math.cos(angle))      # wrap to [-pi, pi]
            if abs(angle) < math.radians(25) and msg.range_min < r < msg.range_max:
                near.append(r)
        self.front = min(near) if near else math.inf

    def control(self):
        cmd = Twist()
        if self.front > self.get_parameter('stop_distance').value:
            cmd.linear.x = self.get_parameter('speed').value          # the way is free: go
        else:
            cmd.angular.z = 0.6                                       # obstacle: turn left on the spot
        self.cmd.publish(cmd)


def main():
    rclpy.init()
    node = SafeDriver()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.cmd.publish(Twist())                                     # stop the robot before leaving
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()
  • qos_profile_sensor_data is the best effort QoS of lesson 2: it matches what laser drivers publish.
  • The two parameters let you tune the robot without editing the code.
  • When the node stops, it publishes a zero speed: never leave a robot with its last command.

If the robot does not move

Type ros2 topic info /cmd_vel. On recent distributions some robots, the TurtleBot 3 among them, expect the type geometry_msgs/msg/TwistStamped (a Twist with a time stamp) instead of Twist. In that case publish a TwistStamped: fill msg.header.stamp = self.get_clock().now().to_msg() and put the speeds in msg.twist. The two types on the same topic do not connect, and there is no error message.

Make it better
  1. Turn to the side where there is more free space (compare the beams on the left and on the right).
  2. Slow down when the obstacle gets close: speed proportional to the distance (a P controller, like in the control course).
  3. Write a launch file that starts the simulation and your node with a YAML file of parameters.
  4. Record a bag of /scan and /cmd_vel, and replay it to check your logic without the simulator.

Check yourself

  1. Why does the laser callback only store a value instead of driving the robot?

    Callbacks must stay short, and the command must be sent at a regular rate by the timer, even if a scan is late.

  2. Why publish a zero speed when the node stops?

    Otherwise the robot may keep executing the last command it received.

  3. The node publishes Twist but the robot expects TwistStamped. What happens?

    Nothing: the types differ, so the publisher and the subscriber do not connect, and the robot does not move.
